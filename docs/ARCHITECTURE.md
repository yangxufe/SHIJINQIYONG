# 先吃 v0.2｜网页架构决策

决策日期：2026-09-25。此文给出设计选择与待验证目标，不宣称已经测试或达到“绝对安全”。事实来源见 `SOURCES.md`。

## 1. 最终选择

**同源、服务器渲染、渐进增强的模块化单体。**

手机 / 电脑浏览器 → HTTPS → Caddy → 本机 Waitress → Django → 本机 SQLite。

Caddy 只把 `/static/` 映射到 `collectstatic` 生成的独立目录，其他应用请求转发给 Django。页面、表单、局部 JSON 请求和静态资源使用同一协议、主机和端口，不启用跨域接口。

| 层 | 选型 | 本次责任 |
|---|---|---|
| 页面 | Django Templates、CSS、少量原生 JavaScript ES modules | 首屏 HTML、普通表单、局部更新；没有必须等待的 SPA 启动阶段 |
| 应用 | Django 5.2 LTS 的当前安全补丁版 | 身份、会话、CSRF、表单校验、ORM、迁移、业务服务与页面 |
| 应用服务器 | Waitress，先用单进程、4 个线程 | 运行同步 WSGI 应用，只监听 127.0.0.1:8000 |
| HTTPS 入口 | Caddy 当前稳定安全版本 | 本地 HTTPS、反向代理、静态资源、请求限制 |
| 数据 | SQLite，本机持久磁盘 | 批次、操作、流水、购物、账号、会话 |
| 测试 | Django 测试工具 / pytest-django、HTTPX、Playwright | 单元、真实文件数据库事务、接口、浏览器和回归 |
| 内容 | 本地 JSON 菜谱 | 无运行时外部 AI API 依赖 |

Python 优先复用仍受支持且满足依赖要求的现有版本；没有合适环境时安装受支持的 Python 3.13 或更新兼容版本的当前维护补丁。记录实际 Python、Django、SQLite 运行库、Waitress、Caddy 版本。`>=5.2,<5.3` 只用于首次解析，交付必须有精确版本锁定，不能把无上限的依赖范围当作锁文件。

Django 官方将 5.2 列为 LTS，延长支持期至 2028 年 4 月；实际安装当日仍需复查支持与安全公告。[S1]

### 为什么调整旧版 FastAPI

旧方案允许自行组合登录、会话、SQL 和 CSRF。此次把安全要求提高后，选择 Django 的内置认证、会话、CSRF、模板转义、ORM 与迁移，可以减少项目内需要自行实现与审查的安全机制。[S2–S5]

这不是说 FastAPI 天生不安全或 Django 自动安全，而是本项目的工期与开发面取舍。Django 不自动提供本项目所有对象权限，也不内置完整的登录尝试节流；这些必须配置、补齐并实测。[S3]

### 为什么不选其他结构

今天不选 React/Vue SPA + 独立 API：本产品主要是列表、表单和少量确认操作，暂不承担另一套构建、状态同步与鉴权集成。不是否认 SPA 的能力。

今天不选微服务、Redis、消息队列、云数据库、强制 Docker：当前只部署一家、一个主机，先把故障面收小。已有成熟容器环境也不在最后阶段重构现有路线。

今天不做浏览器离线写入或 PWA Service Worker：库存是多人共享的服务器事实，不能把设备缓存误当成成功保存。断开互联网但保留局域网应可使用；断开与服务器的连接不能继续写入。

未来需要多实例、多主机或持续高并发写入时，先测量锁等待与业务负载，再考虑 PostgreSQL；不把“用户增长”直接等同于需要微服务。

## 2. 规模与性能预算

基本验收沿用单家庭、5 台常用客户端、200 条在库批次；增加 1,000 批次、10,000 条流水的合成数据回归。用普通本地 SSD 主机、实际家庭 Wi-Fi 测试并记录硬件，不据此要求用户购买设备。

| 指标 | 待验证目标与条件 |
|---|---|
| 首屏冷缓存传输 | HTML + CSS + JS 合计目标 ≤ 200 KB，无图片、字体或框架 CDN |
| LCP | ≤ 2.5 秒；真实目标手机测量，不以开发电脑代替 |
| INP | 有足够真实交互样本时参考 ≤ 200 毫秒；没有样本不得虚构 |
| CLS | ≤ 0.1；为提示区和按钮状态预留空间 |
| 本地交互反馈 | 点击后目标 100 毫秒内出现“提交中”，不是虚假成功 |
| HTTPS 读取 API | 暖态端到端 p95 目标 ≤ 300 毫秒 |
| HTTPS 普通写入 API | 暖态端到端 p95 目标 ≤ 500 毫秒；密码哈希与备份单独测量 |
| 合成负载 | 最多 10 个虚拟用户、总计 10 请求/秒、持续 60 秒；报告全部错误和锁等待 |
| 正确性 | 不出现负库存、重复流水或半成功提交；故意触发的 409 单独统计 |

LCP、INP、CLS 阈值参考 Web Vitals；其真实用户判定要看第 75 百分位等条件。当天小样本实验不能冒充线上用户数据；Lighthouse 单次得分或 TBT 也不等同于真实 INP。[S6]

### 流畅度具体措施

服务器先输出可用页面；核心录入和扣减保留普通表单路径。JavaScript 只增强搜索、确认与小范围更新；失败时保留输入。列表默认分页 50 条，最大 100 条；流水也分页。

筛选防抖约 250 毫秒，废弃过时的查询响应，避免较慢旧请求覆盖新结果。写操作提交后只更新相关卡片或重新读取当前列表，不进行整页大树重建。

不缓存动态家庭页面与 API：统一 `Cache-Control: no-store`。只给内容指纹静态文件长期缓存；公开静态资源可压缩。含会话、CSRF token 或用户数据的动态响应不放入共享缓存，不为了传输体积给它们启用通用压缩。

查询按真实需求设置组合索引；使用 `select_related` / `prefetch_related` 避免循环触发 N+1 查询。批次、流水和购物查询都设置数量上限，日志和测试数据不会无限增长。[S7]

Waitress 的 4 线程是初始设置，不代表 4 个写操作能同时提交；不要靠增加线程或进程掩盖慢查询、长事务或 SQLite 写竞争。[S8, S9]

## 3. SQLite 正确性与版本底线

数据库只在服务端本机磁盘，不放到 SMB/NFS/云盘同步文件夹，不由手机直接读文件。WAL 可以改善读写并行，但仍然只有一个写入者可提交；短事务和锁冲突处理仍必需。[S9, S10]

**2026 年版本核验：** SQLite 官方记录了 WAL-reset 修复：3.51.3 起修复，另有 3.44.6、3.50.7 分支回补。要检查当前 Python 实际加载的 `sqlite3.sqlite_version` 及发行方补丁，不能拿系统命令行 sqlite 的版本代替，也不能以为更新 Django 就会更新 SQLite。[S9]

未能证实运行库已修复时，不启用 WAL。优先升级受支持运行环境；若当天环境受限，可以显式选择 rollback journal/DELETE 模式，并重新测试性能与并发，写明差异。不要手工替换不明来源 DLL 或安装名字相似的“sqlite3”包。

数据库配置原则：`transaction_mode=IMMEDIATE`；只在业务服务内部对必要写入使用短 `transaction.atomic()`；不启用整站 `ATOMIC_REQUESTS`。锁等待先限制为约 2 秒并测量，不能靠 30 秒或无限等待让页面卡住。已确认是瞬时锁忙时返回明确的 503/Retry-After；其他数据库故障不能伪装成可重试冲突。[S11]

Django 在 SQLite 上的 `select_for_update()` 没有行锁效果，不能把这行代码当成并发保障。用版本号、带条件的 `UPDATE`、数据库约束和事务实现防超扣，并用真实文件数据库多连接测试。[S11]

数量使用固定倍率整数：例如 1 个 = 1000 个的千分之一。接口接受有限长度的十进制字符串、最多三位小数，校验后转换为整数；拒绝负数、NaN、Infinity、布尔值和越界值。不同单位不隐式换算；允许明确的同维换算也必须经过单独测试。

所有业务变更包含唯一请求编号、操作类型、规范化参数摘要、操作者、结果与时间。同一个操作者的相同编号同参数重试返回原结果；相同编号不同参数返回 409。**两个不同编号但指向同一购物项的“转入库”仍必须只能成功一次。**

库存变更、流水和幂等结果在同一个事务提交；多批次有一项失败则全部回滚。重复批次行应在校验前规范化合并或直接拒绝，不能借重复行绕过库存检查。对同一批次所有变更，包括元数据编辑，都增加版本号。

## 4. 安全设计与明确边界

### 4.1 要防的风险

未授权局域网访问、跨站诱导写入、恶意食材文本造成脚本执行、错误身份/权限判断、伪造代理头、登录暴力尝试、凭据与备份泄漏，以及并发/重试造成数据破坏。

今天不是公开互联网服务，不覆盖已被完全控制的主机或手机、不可信系统管理员、大规模拒绝服务攻击、企业合规认证或跨家庭隔离。共享家庭成员对共同库存可见是产品设计，不是每人私有库存。

### 4.2 可信 HTTPS 是上线前提

Caddy 通过内置 CA 为实际局域网 IP 或受控内部域名签发证书，客户端必须信任正确的根证书。[S12]

默认采用实际保留的局域网地址访问，避免强制配置内网 DNS。不要把示例地址写成用户的地址。设备、路由与地址选择由实施者在现场核实。

通过可信渠道分发**公开根证书**，对照服务器显示的 SHA-256 指纹；每部手机/电脑需要用户安装并确认信任。不能关闭浏览器校验、接受永久证书警告或以 `verify=False` / `curl -k` 通过验收。CA 私钥和中间证书私钥绝不发给客户端或放进交付包。安装根证书涉及设备信任权限，不能由 AI 宣称已经替用户操作。

Caddy 服务账号、数据目录和 CA 持久路径从第一阶段固定，避免正式托管时使用另一个账号生成另一套根证书。它可以管理续签，但不能保证自动替所有客户端建立信任。[S12]

只有 Caddy 的 443 对允许的家庭子网开放。80 可仅用于跳转，非必需；8000、Caddy 管理端口和数据库不对 LAN 开放。核验 IPv4、IPv6 和其他网络接口，不能只看一条 Windows IPv4 规则。

不关闭整个防火墙、不做公网端口映射、不绕过学校/公司/访客网隔离。开发用 HTTP 仅限 loopback 与合成数据，不能作为家庭上线结果。

### 4.3 身份与请求保护

使用 Django 内置 auth 与数据库 session，不手写 JWT、加密、密码哈希或会话框架。每位成员独立账号；2026-10-03 优化增加管理员邀请注册，邀请码经 Django 签名、有效 24 小时、在 SQLite 短事务中只消费一次，新账号仅有成员权限；不开放无需邀请的公开注册或邮箱找回。账号禁用和恢复继续使用本机管理命令，管理员与成员权限分开。

密码采用 Django Argon2PasswordHasher / Argon2id，保留需要的安全旧格式验证支持；用框架表单/管理命令执行密码校验，不能只调用 `create_user` 就假定校验生效。初始密码交互输入，不用默认密码、命令行明文参数或日志。[S4]

启用兼容且核验过的 django-axes 数据库模式，或已审查的等效组件；按账号与真实来源 IP 分别限制失败尝试，短时冷却、本地解锁。不能只在浏览器节流，也不能因为所有请求都显示为代理地址而连坐全家。此功能并非 Django 默认自带。[S3, S13]

Cookie：会话 `__Host-xianchi_session`，`Secure=True`、`HttpOnly=True`、`SameSite=Lax`、`Path=/`、不设 Domain。CSRF Cookie 也设 Secure、SameSite，设置 HttpOnly 后，前端从 Django 模板隐藏字段读取 CSRF token，不读 Cookie。没有 localStorage token、没有长期写入浏览器的家庭库存镜像。[S5, S14]

Django CSRF 中间件覆盖登录、退出和所有不安全 HTTP 方法；普通表单用 csrf_token，fetch 用 X-CSRFToken。同源不是 CSRF 防护的替代，CORS 也不是授权。[S5, S14]

所有业务页面与接口默认需要登录，例外为未登录欢迎页、登录、邀请注册页、最小健康检查和必要静态文件。网页未登录跳转登录；API 返回结构化 401，不把登录 HTML 当成成功 JSON。退出使用 POST，撤销服务器会话。会话有效期初设 8 小时，SESSION_SAVE_EVERY_REQUEST=False，避免每个读取请求都刷新会话写入；禁用账号/改密码后的旧会话行为必须测试。

`DEBUG=False`；随机 SECRET_KEY 来自受限配置；`ALLOWED_HOSTS` 和受信来源为明确值，不用通配。生产不开放 Django admin、调试工具或自动 API 文档。只暴露最小健康状态，不输出路径、版本明细、账号或连接参数。

### 4.4 代理、输入和浏览器防护

Caddy 覆盖来源 IP 与协议代理头；Waitress 只信任 127.0.0.1 这一跳及必要的转发头，清除其他不可信头；Django 的 secure 判断和真实来源必须实际验证。不能信任任意客户端提供的 X-Forwarded-For/Proto；不能用 `trusted_proxy='*'` 简化配置。[S8, S15]

模板保持自动转义，原生 JS 用 textContent 或受控 DOM 构造；不把名称、备注或错误信息塞进 innerHTML，不对用户内容使用 safe/mark_safe。[S2]

部署 CSP：`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`。不用 unsafe-inline / unsafe-eval；所有脚本与样式外置。配合 nosniff、DENY、same-origin Referrer-Policy 和禁用摄像头/麦克风/地理位置的 Permissions-Policy。CSP 是补充，不替代转义。[S16]

在实际域名与证书信任验证后再设置 HSTS；纯 IP 不把 HSTS 当成可靠保护。今天不启用 preload 或盲目 includeSubDomains。对 `check --deploy` 的每个警告解释并处置，不屏蔽检查制造“全绿”。[S18]

无上传功能，应用请求体先限制 64 KiB；前后端都限制名称、备注、查询长度、单次批次数和分页大小。SQL 参数化；不接受客户端指定的数据库路径、任意模型字段或任意排序表达式。

### 4.5 数据、日志与更新

业务数据库、备份、日志、配置、CA 数据都在静态目录之外。运行进程用专用低权限身份；只允许读代码、读写自己的数据目录。不要声称普通 SQLite 文件已经加密。

主机盘与异设备备份优先放在操作系统已启用且已验证的加密存储上，记录实际状态；磁盘加密不防已经登录主机的恶意进程。没有验证过的保护要列为限制，不能凭“使用 HTTPS”推断静态数据已加密。

日志不记录密码、Cookie、CSRF token、请求正文、查询字符串或真实家庭清单；记录请求编号、路由模式、状态、耗时与脱敏错误。Caddy访问日志也需核查敏感头与查询参数，不只检查应用日志。设置轮转和容量上限。

核验主机操作系统仍有适用安全更新、磁盘与时钟状态正常。依赖锁定后运行已核验工具检查已知漏洞；Python 依赖扫描不覆盖所有 OS、Caddy 和内嵌 SQLite 风险。无扫描结果不等于零漏洞。发现适用的高危/严重问题阻断发布；修复后回归，不在最后阶段无依据升级整套技术栈。

## 5. 备份、恢复与运行

使用 Python sqlite3 backup API 生成独立快照，检查完整性与外键；不在 WAL 运行时只复制主文件。[S17]

恢复默认写到独立新目录，不能覆盖运行中的数据库。真实切换前停止服务、保留旧 data 目录、避免旧 WAL/SHM 混入，核对迁移版本、批次与流水。清除恢复数据库里的全部旧会话，复核/重置账号状态，避免让早已退出或禁用的凭据重新生效。

保留异设备的加密备份；恢复时间点之后的变更可能丢失，必须注明。备份可以包含账号哈希与会话等敏感数据，禁止作为普通附件发送。

Waitress 与 Caddy 各自由实际系统的服务/任务计划托管；固定工作目录、解释器、环境变量、证书数据路径，设置退出重启，限制重启频率并保存脱敏日志。测试关掉终端、终止进程和重启主机后的恢复，不能用 runserver / --reload 交付。

## 6. 固定产品边界

四个入口：今天、冰箱、做什么、采购；基础操作记录与设置是次级页。单家庭数据共享，无多家庭平台，无付款、图片/OCR、推送、离线编辑、第三方订单、在线 AI。

批次分开、最多三位小数、计划/包装/采购/开封日期分开。食品状态只描述记录与待核对，不描述食用安全结论。疑似变质、包装日期已过、储存状态待核对的批次不进入可用推荐；不能用“修改日期”自动解除疑似变质状态。

缺计划日期不自动意味着变质；缺包装日期也不自动意味着不能使用。对无包装新鲜蔬菜，提供“不适用”日期状态，但仍要求用户核对储存与食材状况；这是用户记录，不是应用安全认证。

本地菜谱按真实可用批次匹配，名称用显式别名表，不让模型猜测数量。选择菜谱不扣库存，确认实际用量才扣。“用于做饭”不同于“直接吃掉”。采购“买到了”不同于“已入库”。不推算无依据的节省金额、减废重量或碳减排。

## 7. 发布门槛

可信 HTTPS、独立账号、CSRF、权限、输入/XSS、防超扣/幂等、多批次回滚、重启持久化、备份恢复与真实双设备访问均须有证据。第六小时之后只修复，不用安全降级换取绿色页面。

性能目标未达到但正确性与安全通过时，必须给出具体测量与限制，再决定是否有限试用；安全或数据完整性阻断未解决时，不供家人持续使用。

## 8. 拍照录入的用户变更（2026-09-25）

用户在阶段 04 手机验证后要求同时识别散装食材和包装文字，并简化日常录入。本节替代上文第 4.4 节“无上传功能”、第 6 节“无图片/OCR”和禁止摄像头的原产品边界；其余身份、HTTPS、数据完整性与本地运行约束仍适用。

- 页面用手机文件选择或相机拍摄，浏览器把照片缩小、转为 JPEG；只有 `/api/inventory/recognize/` 可提交最多 4 MB 请求体。Caddy 对其他路由仍限 64 KB，Waitress 对所有路由上限 4 MB；服务端再限制图片字节数、像素数和格式。
- 服务端只向 `127.0.0.1:11434` 的已安装 Ollama `qwen3-vl:8b` 模型发送去元数据的照片；不调用在线 AI，不把照片、模型描述或识别结果写入数据库或静态目录。此进程是同机识别辅助，不提供 LAN 入口。断网时运行依赖本机已存在模型。
- 识别只给一个食材名称建议；照片不能可靠判断真实数量、包装日期、储存状态或食物是否安全。成员核对名称、填写实际数量并确认后，才通过原库存服务的事务、幂等和流水入库。识别失败时保留普通手工表单。
- `Permissions-Policy` 只允许同源摄像头，麦克风与地理位置仍禁用。手机相机入口的兼容性和真实照片准确性需在设备上验证。

## 9. 家庭菜谱与教程收藏的用户变更（2026-09-25）

用户在阶段 05 后要求：菜谱按当前食材排序并分类；家庭成员能保存自写菜谱、网上视频/文字/图片教程链接，也能上传图片和原视频。本节替代上文第 4.4 节对持续上传的 64 KiB 通用边界及第 6 节“本地 JSON 菜谱为唯一内容”的范围；其余独立账号、可信 HTTPS、服务器事实、事务库存和禁止在线 AI 的要求保持有效。

- 内置菜谱继续使用本地 JSON。家庭成员新增或编辑的标题、主要食材、步骤、自由分类、标签、来源链接与笔记存 SQLite。系统只有一个家庭，所有具备家庭角色的成员共享这些记录；匿名与无家庭角色账号一律不能读写。未来若改为多家庭，必须先引入明确的家庭外键与隔离测试，不能直接复用本单家庭表。
- 搜索按钮由浏览器在成员主动点击后打开外部搜索页面。应用服务器不抓取网页、不自动下载或嵌入外站内容；成员核对后手工保存 HTTPS 链接和自己的笔记。外部站点内容可能改变或不可用，且打开外链会向该站点发送成员输入的关键词。保存的笔记和本机上传文件只通过认证后的本机路由读取。
- 图片限制为每道菜最多 6 张，输入最多 8 MiB/2,000 万像素，服务端统一重编码为 JPEG 并去除源图元数据。视频限制为每道菜 1 个、单个最多 200 MiB，只接收 MP4/MOV/WebM 的相应容器头；不转码，播放能力依设备而异。视频按原字节保存在私有 `data/recipe_media/`，可能保留原视频元数据。文件名为随机不透明值，不使用用户文件名，不放在 Caddy 静态目录；认证路由按需返回图片或支持单段 Range 的视频响应。
- Caddy 仅对 `/recipes/family-*/upload/` 放宽请求体到 220 MB，照片识别仍为 4 MB，其余应用路由仍为 64 KiB；Waitress 全局接收上限相应增至 220 MB，仅 loopback 可达。Django 将大文件暂存于受限数据目录。媒体上传与菜谱创建分别使用持久请求编号处理重复提交；图片/视频数量限制在数据库事务内检查。
- 匹配只看真实可用批次，已知别名精确归一，其他食材精确名称匹配；默认按匹配比例和匹配种类数排序。选择或保存菜谱不更改库存，确认实际用量继续复用 `apply_action` 的事务、版本、幂等与流水。家庭菜谱编辑有版本检查，已提交做饭请求即使之后编辑菜谱也可用原编号重试。
- 备份必须同时包含 SQLite 与所有被数据库引用的媒体文件。`backup_household` 要求先停止 Waitress，再用 SQLite backup API 建快照、检查完整性与外键、逐个核验附件 SHA-256 后生成私有目录；此目录不进入源码 ZIP。异设备保存与恢复演练仍需人工完成。

## 10. 阶段 06 采购闭环（2026-09-25）

- 单家庭采购项以“待采购 → 已买到 → 已入库”运行，未完成项可取消。标记买到不建立库存。计划数量与实际入库数量分开记录，单位固定为采购项单位，不做未经核实的换算。
- 添加采购项前，在服务器事务内按本地显式别名或精确名称核对现有批次与未完成清单。同名已有记录时成员必须明确确认仍需购买；跨单位只提示原单位数值，不自动抵扣。疑似变质、储存待核对、包装日期已过的批次仅触发“需核对”提醒，不计为可用库存。
- 每个采购写动作都使用成员和 UUID 请求编号、参数摘要、持久结果、短事务及状态/版本条件更新。实际入库在同一事务内创建批次、正向库存流水与采购项的一对一关联；同编号重试返回原结果，换编号也不能再次入库。新批次默认储存待核对，成员需确认实物状态；页面不代替食品安全判断。
- 采购只增加库存，不假定“买到了”就“已入库”；后续真实使用和丢弃仍走原库存动作。私有生产库迁移前需完成包含 SQLite 与被引用媒体的备份。

## 11. 阶段 07A 有限扩展（2026-09-26）

**跨平台源码交付：**仓库可提供 Windows 与 macOS 的同一 Django 应用代码；各机器的 SQLite、成员账号、附件、运行密钥与 Caddy CA 都在各自私有 `data/`，不进入 GitHub。macOS 另用 `config/Caddyfile.macos` 和 `scripts/macos_*` 初始化当前已确认家庭 IP/CIDR，Waitress 仍仅 loopback，Caddy 仅绑定所填 IPv4 并按来源子网拒绝其他请求。安装证书信任与新网络开放均由机器所有者现场确认；没有证书信任的客户端不能作为正式登录验收。跨机器克隆代码并不构成家庭数据同步。

- 保留 Django 模板单体、Waitress/Caddy/SQLite、原认证与库存事务服务。菜谱工作台读取既有批次和成员权限，不建立第二套库存。原菜谱 ID 与家庭菜谱主键保持稳定；旧名称式菜谱在补齐可信用量前不得被称为严格库存匹配。
- 新增结构化菜谱、个人/家庭偏好、营养参考和生成任务。严格库存模式按必要材料的数量、单位、状态和批次统一分配；未知数量、未经记录的调料与跨维换算使结果待确认或不可行。菜谱浏览、生成和收藏均不扣库存或修改采购，实际使用复用原库存动作。
- 可选模型仅在服务端由管理员配置，默认关闭。受控本机任务进程短事务领任务，模型等待不占 Waitress 线程或 SQLite 写事务；模型输出经过结构、硬约束、库存、营养和教程校验后才展示。模型不能执行数据库或系统命令。无模型时本地匹配仍可用，不能伪装为 AI 结果。
- 本阶段例外覆盖旧文档“不接外部 AI”和早期冻结排期，但不放宽可信 HTTPS、成员身份、CSRF、最小数据发送、私有数据隔离、证书校验与恢复验收。现行入口仍为当前已确认家庭 WLAN 的 IP HTTPS；手机 CA 信任尚未验收，不能据本机请求宣称正式上线。
