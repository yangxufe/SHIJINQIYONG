# 阶段 07A 安全核对

**GitHub 交付补充：**只提交源码、迁移、公开参考 JSON、示例配置与文档；生产 SQLite、附件、`data/runtime.env`、Cookie、日志、CA 根私钥及由 Caddy 管理的证书存储均排除。Mac 首次安装单独生成密钥和 CA；其 Caddy 进程环境不接收 Django 密钥。仓库访问权限由 GitHub 管理，代码下载不会复制原家庭数据。Mac 网络绑定、来源 CIDR 和证书信任流程见 `MACOS.md`；真实 Mac 与手机尚未现场验收。

核对日期：2026-09-26。本文件补充 `ARCHITECTURE.md` 与 `HANDOFF.md`，不替代家庭设备的现场验收。

- 登录、会话、密码、CSRF、登录节流、CSP、动态 `no-store`、原库存版本检查与持久幂等继续由原 Django 模块执行。新增工作台、口味、菜单、反馈和生成任务均处于原登录门后；私人需求和任务按所属成员查对象，家庭菜谱仍为本家庭共享。
- 默认 `SHIJIN_RECIPE_PROVIDER=off`；未配置任何实际模型凭据。仅支持代码固定的 Ollama `127.0.0.1:11434` 与官方 HTTPS 提供者端点。管理员选模型名和凭据；浏览器不能交任意模型 URL。外部发送前需当次明确勾选，发送已确认的必要条件及可用食材名称/数量，不发送原文、成员编号、账户、Cookie、备注或整库。私钥只可放受保护的运行配置，不进入源码、网页、日志或交付包。
- 工作进程只能得到结构化候选。`structured.py` 拦截字段、范围、材料去向、器材、已知不安全操作和部分提示注入；`workbench.py` 重新核对硬限制、可用批次、数量、缺口、营养。未知安全问题仍需人工核验，自动校验并非食品安全认证。需要中心温度的已知食材要求食物温度计和带官方来源的规则编号。
- 生成、浏览、反馈和保存不写库存或购物项；菜单采购需显式选择净缺口，库存动作需再次确认实际量并通过原事务、条件更新和流水。任务 UUID、个人配置、结果页无共享缓存。消费者取消任务后不发布迟到结果；外部供应商可能仍已计费。
- 当前家庭 WLAN 已按此前确认切到 `192.168.110.146/24`：Caddy 仅监听该 IPv4 的 8443，入站规则仅放行 Caddy 程序、WLAN、该地址与同子网；Waitress 仅监听 `127.0.0.1:8000`。原固定 `.local` 名称实验保持禁用。电脑用公开根 CA 严格校验证书后 `/health/` 和 `/login/` 200，匿名 `/api/shopping/`、`/api/recipes/` 401，70 KB 普通请求 413，指纹静态文件 200。没有把证书校验关掉。
- **手机阻断：**用户报告 Android 在当前 IP 打开 `/health/` 仍显示证书警告。该访问不能算可信 HTTPS，更不能作为安全登录或发布验收。需按 `HANDOFF.md` 核对家庭公开根 CA 指纹、在 Android 以 CA 证书方式安装并确认信任后重测；不要越过警告输入密码。手机采购闭环、主机重启、异设备加密备份仍未现场通过。
- `check --deploy` 退出码 0，仅现有 HSTS `security.W004` 警告；按 IP 访问时没有盲目启用 HSTS。`pip check` 和完整回归另见 `PROGRESS.md`。没有执行新的 Windows/Caddy/Ollama 全栈漏洞扫描，不能据 Python 扫描推断它们无漏洞。
